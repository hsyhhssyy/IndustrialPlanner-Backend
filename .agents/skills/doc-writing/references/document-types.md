# 后端专项文档要求

## Stage 文档

Stage 位于 `.docs/stageN/`，其中 `N` 为数字。Stage 总入口至少说明：

- 阶段目标、范围与非目标。
- 当前状态与里程碑。
- 需求索引、FAQ、Bug 和需求正文的导航。
- 已完成事项、未完成事项和最合理的接手起点。
- 哪些是用户硬约束，哪些是阶段策略。

最新编号不自动等于当前活动范围；还要核对 Stage 状态、需求索引和用户目标。

## 需求文档

单需求文档至少维护：

- 唯一编号、名称、优先级、状态和所属里程碑。
- 背景、目标、非目标与当前口径。
- 主业务 Worker、受影响的 HTTP 合约、D1/KV/R2/Service Binding 边界。
- 实施拆解、验收标准、测试记录和未决问题。
- 决策变化的原因与时间线。

状态变化先更新需求正文，再同步需求索引。不能用“代码已写”代替验收完成。

## Bug 文档

证据不足时先记录定位动作，不直接写猜测性修复。至少区分：

- 复现条件和用户现象。
- 已确认事实。
- 高概率推测。
- 缺失证据。
- 下一步最低成本定位动作。
- 根因所属层：HTTP、业务规则、D1、R2、KV、Service Binding、部署或前端合约。

修复完成后补充回归测试、影响范围、未验证环境和是否存在数据修复需求。

## 架构与 ADR

架构文档必须明确：

- Worker 与数据所有权。
- 允许的依赖方向。
- 真相层、事务边界和失败语义。
- Cloudflare 平台约束。
- 安全、性能、迁移和回滚代价。

不得把归档的 Rust、PostgreSQL/MySQL、Redis 或 Kubernetes 架构继续描述为当前实现。

## FAQ

FAQ 只记录跨需求重复出现且已经收敛的规则。单需求特殊决策留在对应需求文档；未经验证的推测不进入 FAQ。

## 执行与验收记录

- 命令、环境、日期和结果必须真实。
- 本地 Miniflare、Wrangler dry-run、Beta 与 Production 验证分别记录。
- 用户验收属于决策记录，不伪装成自动化测试。
- 未执行或因依赖缺失跳过的验证明确列为未验证。
