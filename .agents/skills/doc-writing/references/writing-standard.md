# 后端项目文档通用写作标准

## 目标

项目文档是长期真相层，不是聊天摘要。读者不查看当前对话，也应理解问题、目标、方案、原因、边界、状态和下一步。

## 必须独立成立

- 不写“如前所述”“见对话”“按刚才讨论”等依赖聊天上下文的表述。
- 影响实现、重构、排障、测试或交接的信息必须直接写入文档。
- 只写已确认事实；不把推测、计划或用户验收伪装成已实现行为。

## 解释原因与取舍

重要结论至少说明：

1. 要解决什么问题。
2. 为什么选择当前方案。
3. 明显替代方案为什么未采用。
4. 当前方案的代价、限制和调整边界。

不要只记录“做了什么”。

## 区分决策来源

关键规则尽量标明来源：

- 【用户明确要求】：用户确定、默认不可擅自改变。
- 【阶段约束】：只在当前 Stage 或迭代内生效。
- 【现状约束】：来自代码、运行时、协议、Cloudflare 平台或部署现状。
- 【AI / 开发者决策】：为完成目标作出的实现选择，未来优先允许调整。

发生冲突时，先调整实现者决策，再评估阶段安排；不得因实现不方便直接推翻用户要求。

## 后端真相层

- 当前架构以活动文档、当前代码、`wrangler.toml`、migration、TypeScript 合约和测试共同为准。
- D1、KV、R2、Service Binding、HTTP 请求态和 Worker 实例内存必须明确区分。
- API 路径、字段、错误码和数据所有权不得用内部临时命名代替。
- `.docs/common/双数据库支持设计.md` 已归档，只能作为历史背景，不能驱动 Cloudflare Workers 当前实现。
- 文档与代码冲突时，不静默选择一方；记录冲突证据并先收敛真相层。

## 内容结构

重要设计或需求文档通常应包含：

1. 背景与问题定义。
2. 目标与非目标。
3. 当前事实与决策来源。
4. 核心方案、数据流和责任归属。
5. 异常、并发、幂等、安全和失败语义。
6. 替代方案与未采纳原因。
7. 测试与验收标准。
8. 风险、未决项和未来调整入口。

只保留与文档职责有关的章节，不为形式完整制造空内容。

## 一致性

- 方向变化后直接删除 Markdown 中的过时表述，不能让旧方案与新方案并存。
- 同一事实只保留一个真相入口；其他文档链接到该入口。
- 状态、索引、需求正文和测试记录应同步。
- 局部 Bug 先判断是否暴露共享合约、数据库约束或跨 Worker 边界问题，不把系统性缺陷写成路径特例。

## Submodule 边界

`.docs` 是独立 Git submodule：

- 修改前分别检查根仓库与 `.docs` 仓库状态。
- 不覆盖文档仓库内既有未提交改动。
- 文档变更与代码变更属于同一交付，但提交和推送仍需用户明确授权。

## 安全与可公开性

- 不写入 `.dev.vars`、部署配置、token、secret、真实用户数据或完整 R2 key。
- 示例使用明显虚构且不可复用的值。
- 记录环境验证时区分本地 Miniflare、Beta 和 Production，不把其中一个环境的结果扩展为另一个环境的事实。

## Markdown 删除规则

Markdown 不适用代码的 `AI-REMOVED` 注释化删除规则。已失效内容直接物理删除；必要的历史过程写入明确的时间线或归档文档，而不是藏在注释中。
