# 后端更新日志写作规范

## 内容边界

更新日志面向 IndustrialPlanner 最终用户，只记录用户能够感知的后端行为：

- 新增或改变的同步、下载、账户、资产、OAuth、遥测能力。
- API 行为变化最终反映到客户端的功能。
- 用户实际遇到的错误修复、稳定性或性能改善。

以下内容不得写入更新日志：

- AI 指令、Skill、CI、构建、目录调整、依赖升级和纯重构。
- 用户无法感知的数据库表、索引、repository 或内部 Service Binding 实现。
- changelog 自身更新。
- 未上线、未验收或仅存在于计划中的能力。

## 信息来源

1. 先读取目标版本已有日志及 `public/changelog/index.json`。
2. 需要从提交生成时，读取上一正式版至目标版本之间的 `feat:` 和 `fix:` 提交。
3. 用当前代码、HTTP 合约、migration 和测试确认行为，不能只凭提交标题扩写。
4. 涉及前端实际表现时，只描述已有证据支持的终端现象；不得读取另一仓库来补猜行为，除非用户另行授权。

## 结构与措辞

- 完整版本日志沿用现有格式：
  - `# 增量更新 v<version>`
  - `## 新功能`
  - `## 问题修复`
- 只出现一类内容时可省略空章节。
- 每条以 `- ` 开头，简洁描述用户能做什么或不再遇到什么。
- 最终正文不必保留 Git 提交的 `feat:` / `fix:` 前缀。
- 修复项描述用户看到的错误现象，不描述 SQL、CAS、HMAC、D1/R2 切换等内部根因；只有理解行为必须时才使用稳定的公开协议名。
- API、字段、错误码和领域对象名称必须来自现有 HTTP 合约、TypeScript 类型、migration 或实际响应，不得自行翻译或编造。
- 不得展示 token、secret、用户数据、内部对象 key 或可用于攻击系统的实现细节。

## 用户手写内容

- 用户手写的标题、引言、章节、条目和结语只读，不得改写。
- 自动补充内容放入合适的既有章节；无法归类时放入 `## 其他改动`。
- 插入前通读全文，已经由用户描述的功能或修复不得重复。

## 索引

创建版本文件后同步更新 `public/changelog/index.json`：

- `version` 与文件标题、tag 使用同一版本。
- `file` 必须精确匹配实际文件名。
- `date` 使用确认的发布日期；无法确认时不得猜测。
- 保持 JSON 有效，并沿用现有版本排序。

## 风格与配图

- 语气清晰、自然、面向用户，不卖惨、不自我贬低、不抱怨外部项目。
- 本仓库是后端项目，不使用 Playwright、浏览器截图或 UI 占位图。
- 不把技术实现清单伪装成产品价值。

## 完成检查

1. 版本号、文件名和索引一致。
2. 所有条目均已实现并有证据。
3. 无纯内部改动、重复条目或敏感信息。
4. 用户手写内容未被修改。
5. Markdown 与 JSON 格式有效。
