## 禁止修改测试

### 定义

以下类型的错误**绝对不允许**直接修改测试代码来“修绿”：

- **测试断言失败（test failed）**：即测试逻辑未通过，期望值与实际值不匹配。
- **运行时异常**：测试执行过程中抛出的未捕获异常、panic、超时或外部依赖连接失败。

### 允许直接修复的错误

以下类型属于代码正确性问题，**可以直接修改**，无需询问用户：

- **Rust 编译错误（compile error）**：类型不匹配、trait 未实现、缺少导入、模块接口变更导致的编译错误。
- **格式或 lint 错误**：`rustfmt`、Clippy 或 CI 规则违反。

### 测试失败时的处理流程

测试失败可能原因：

1. **测试漂移**：实现经已授权的接口/行为变更后，测试期望值未同步更新。
2. **回归失败**：实现变更引入真实 bug。
3. **环境失败**：隔离 PostgreSQL、MySQL、Redis、网络或 Kubernetes 测试依赖未准备好或本身异常。

当测试失败时，必须：

1. **进行初步原因判断**，区分测试漂移、回归失败和环境失败。
2. **通知用户**，告知：
   - 哪些测试未通过；
   - 每个测试验证什么行为；
   - 初步判断的失败原因；
   - 若为环境失败，缺少或异常的隔离依赖。
3. **等待用户指令**，不得擅自修改测试断言、测试逻辑或外部环境配置来掩盖失败。

### 随模块变更同步修改测试（允许）

当用户明确要求修改某个模块的实现时，对应测试可以同步更新。
此时修改测试的前提是：修改原因是“模块接口/行为变更”，而非“测试未通过”。

执行结束后必须列出：

- 修改了哪些测试模块；
- 每个测试模块验证什么行为；
- 是因为什么模块的什么变更触发本次测试修改；
- 是否仍有需要真实 PostgreSQL、MySQL、Redis 或 Kubernetes 环境才能验证的边界。

## 创建新测试

创建新测试时，请阅读：

`.docs/common/测试/测试架构设计通则.md`

### 测试文件位置与命名

- 纯逻辑单元测试优先放在被测 Rust 模块的 `#[cfg(test)] mod tests` 中。
- 需要 HTTP、PostgreSQL、MySQL、Redis、并发或多个模块公开接口的测试放在 `tests/` 下对应子目录。
- 文件使用 Rust 的 `.rs` 扩展名，并以被测能力命名，例如 `tests/api/sync_shadow_telemetry.rs`。

### 运行命令

```bash
cargo fmt --check
cargo clippy --all-targets -- -D warnings
cargo test --locked
```

需要外部依赖的测试必须显式声明并校验 `TEST_DATABASE_URL`、`TEST_REDIS_URL` 或专用 Kubernetes namespace；未提供时只能报告环境未满足，不得回退连接普通 `DATABASE_URL` 或 `REDIS_URL`。

### 分层策略

不同模块的测试策略参见 `测试架构设计通则`：

- **Telemetry 合约**：纯 JSON/Rust 类型单元测试，覆盖前端真实请求与拒绝边界。
- **API**：真实 HTTP 请求，验证路由、CORS、状态码和响应头。
- **关系型数据库**：分别针对 PostgreSQL 与 MySQL 运行真实 migration、约束、幂等和故障语义。
- **Redis / 分布式**：真实 Redis，验证跨实例限流、降级和可信代理边界。
- **Kubernetes**：静态清单验证；需要集群验证时只用独立临时 namespace。
