## 禁止修改测试

### 定义

以下类型的错误**绝对不允许**直接修改测试代码来"修绿"：

- **测试断言失败（test failed）**：即测试逻辑未通过，期望值与实际值不匹配。
- **运行时异常**：测试执行过程中抛出的未捕获异常、超时或外部依赖连接失败。

### 允许直接修复的错误

以下类型属于代码正确性问题，**可以直接修改**，无需询问用户：

- **TypeScript 编译错误（compile error）**：类型不匹配、缺少导入、模块接口变更导致的编译错误。
- **格式或 lint 错误**：ESLint、Prettier 或 CI 规则违反。

### 测试失败时的处理流程

测试失败可能原因：

1. **测试漂移**：实现经已授权的接口/行为变更后，测试期望值未同步更新。
2. **回归失败**：实现变更引入真实 bug。
3. **环境失败**：Miniflare 本地模拟环境未准备好或本身异常。

当测试失败时，必须：

1. **进行初步原因判断**，区分测试漂移、回归失败和环境失败。
2. **通知用户**，告知：
   - 哪些测试未通过；
   - 每个测试验证什么行为；
   - 初步判断的失败原因；
   - 若为环境失败，缺少或异常的依赖。
3. **等待用户指令**，不得擅自修改测试断言、测试逻辑或外部环境配置来掩盖失败。

### 随模块变更同步修改测试（允许）

当用户明确要求修改某个 Worker 的实现时，对应测试可以同步更新。
此时修改测试的前提是：修改原因是"模块接口/行为变更"，而非"测试未通过"。

执行结束后必须列出：

- 修改了哪些测试文件；
- 每个测试文件验证什么行为；
- 是因为什么模块的什么变更触发本次测试修改；
- 是否仍有需要 Miniflare D1/KV/R2 Service Binding 环境才能验证的边界。

## 创建新测试

创建新测试时，请阅读：

`.docs/common/测试/测试架构设计通则.md`

### 测试文件位置与命名

- 纯逻辑单元测试优先放在被测文件同目录的 `*.test.ts` 中。
- 需要 HTTP、D1、KV、R2、Service Binding 或多个 Worker 公开接口的测试放在 `tests/` 下对应子目录。
- 文件使用 `.test.ts` 扩展名，并以被测能力命名，例如 `tests/http/sync.test.ts`。

### 运行命令

```bash
pnpm lint
pnpm test
```

单个 Worker：

```bash
pnpm --filter <worker> test
```

需要 Miniflare 的集成测试必须确保本地已安装 `better-sqlite3` 等原生依赖；若环境不支持，只能报告环境未满足，不得跳过测试或伪造通过。

### 分层策略

不同模块的测试策略参见 `测试架构设计通则`：

- **合约/纯逻辑**：Vitest 单元测试，覆盖 JSON 反序列化、JWT 验证、限流算法等。
- **HTTP**：Miniflare `dispatchFetch`，验证路由、CORS、状态码和响应头。
- **D1**：Miniflare 本地 D1 模拟，执行真实 migration 后验证事务、唯一约束和回滚。
- **KV**：Miniflare 本地 KV 模拟，验证 TTL、过期和降级语义。
- **R2**：Miniflare 本地 R2 模拟，验证预签名 URL 和对象完整性。
- **Service Binding**：Miniflare 多 Worker 模式，验证跨 Worker 调用和 JWT 透传。
